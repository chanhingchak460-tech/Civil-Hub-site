Sensors, small computers, networks and models working together under real constraints. The subject is less about the cleverest algorithm than about latency, energy, bandwidth and freshness, and what those trade-offs mean for connected infrastructure.

01The loop, not the device

AIoT puts inference close to where data is made. A system senses with transducers, conditions the signal on a microcontroller, moves it over a network, and acts on a decision.

What separates it from ordinary IoT is that a model makes the decision, often on the device itself. The design question is never accuracy alone: it is accuracy per unit of energy, latency and bandwidth.

A bridge strain sensor reporting in milliseconds solves a different problem from a soil probe that wakes once an hour.

Nyquist sampling rule
\[f_s > 2 f_{\max}\]
sample above twice the highest frequency of interest, or fast vibration aliases into a false slow wave

02Sensing, sampling and the microcontroller

A sensor converts a physical quantity into an electrical signal, and an ADC turns that into numbers at a fixed sampling rate. Real readings carry noise and drift, so calibrate against a reference and filter, remembering that every filter adds delay.

A microcontroller provides GPIO pins, timers and buses such as I²C and SPI for local chips, and it must be duty-cycled: radio and sensing dominate the power budget, so sleeping between samples is what makes a battery last for years.

ADC resolution
\[\Delta V = \frac{V_{\mathrm{ref}}}{2^n}\]
the smallest voltage step for an n-bit converter; a real reading is usually several steps

03Networking choices

No single radio fits every deployment. Above the link layer, MQTT is the usual messaging pattern: devices publish to a broker on a topic such as site/42/temperature, and subscribers receive it.

QoS levels 0, 1 and 2 trade duplicates against delivery guarantees, and a retained message stops a late subscriber from seeing stale state.

Publishing a reading with MQTT
client.publish('site/42/strain', payload, qos=1) client.subscribe('site/42/command')
qos=1 gives at-least-once delivery, so the handler must tolerate duplicates

04Protocols beyond MQTT

MQTT is not the only way to move bytes. CoAP shrinks HTTP's request–response model onto UDP for constrained nodes, with confirmable messages and an observe mode for server push; it suits a battery sensor behind a gateway rather than a chatty web app.

Plain HTTP/REST is easy to debug and integrate but verbose per message; WebSockets keep a persistent channel for live dashboards; AMQP adds enterprise routing for fleets of gateways.

Choose by constraint, not habit: payload and header overhead, connection state, delivery guarantee, and whether the network is IP end-to-end or needs a gateway translation. A protocol that assumes always-on TCP is a poor fit for a node that wakes once an hour.

05Edge or cloud

Inference can run on the device, at a gateway, or in the cloud. Pushing it closer cuts latency and bandwidth but limits model size and energy. End-to-end latency is the sum of the stages, and the slowest stage dominates.

Model compression makes edge inference practical: quantisation stores weights in 8 bits instead of 32, pruning removes small weights, and both cost a little accuracy. Treat the choice as a trade curve rather than a slogan.

End-to-end latency
\[L = t_{\mathrm{sense}} + t_{\mathrm{queue}} + t_{\mathrm{compute}} + t_{\mathrm{network}}\]
measure each stage; optimising the wrong one buys nothing
Service capacity
\[C = \frac{1}{t_{\mathrm{service}}}\]
in samples per second when the service time is in seconds

06Learned controllers: from rules to gradients

On-device AI is often a learned controller rather than a vision model. A rule-based layer switches on fixed thresholds; a learned layer computes a linear score from features and turns it into a probability with the sigmoid function.

Training finds the weights by descending the gradient of the cross-entropy loss, which punishes confident mistakes far more than hesitant ones.

The workflow matters as much as the maths: collect labelled behaviour from a working controller, extract the same features at run time, train offline, then run the small model online. Because the model learns a decision pattern rather than the physics, it reproduces the teacher's behaviour without understanding the room — which is exactly why the training data must cover the edge cases.

Linear score
\[s = w_1 x_1 + w_2 x_2 + w_3 x_3 + b\]
features x computed from recent readings; s = 0 is the decision boundary
Sigmoid probability
\[p = \frac{1}{1 + e^{-s}}\]
p is the predicted probability of the positive class
Cross-entropy loss
\[l = -[y\ln p + (1-y)\ln(1-p)]\]
y ∈ {0, 1} is the label; a confident wrong answer costs a large loss
Gradient update step
\[w \leftarrow w - \eta (p - y) x\]
η is the learning rate; one small step per training sample

07Streaming, queues and freshness

Sensor data arrives continuously, so an AIoT system is a queueing system. As the arrival rate approaches the service rate, waiting time explodes: at 80% utilisation a queue is already four times longer than at 50%.

Admission control decides which samples to drop when the queue is full, which is how the system protects itself under overload. Another useful measure is the age of information, the age of the newest processed sample. Very accurate inference on stale data is worse than a rough answer that is current.

Utilisation
\[\rho = \lambda t_{\mathrm{service}}\]
ρ must stay below 1 for a stable queue
Little's law
\[L = \lambda W\]
mean items in the system equal arrival rate times mean time in the system
Mean waiting, M/M/1 queue
\[L_q = \frac{\rho^2}{1 - \rho}\]
diverges as ρ approaches 1

08Real-time scheduling on small cores

An edge node that must sample, transmit and infer on schedule is a real-time system: each task has a period and a worst-case execution time, and a deadline it must never miss. The first check is utilisation, the sum of execution time over period for every task.

Rate-monotonic gives the shortest-period task the highest priority and is provably optimal among fixed-priority schemes; earliest-deadline-first orders by remaining deadline and can keep a single processor busy up to full utilisation.

Questions usually give a task table and ask whether the set is schedulable: compute the utilisation, compare it with the bound, and for rate-monotonic also check each task's response time. Missing a deadline in infrastructure monitoring means a dropped alarm, so scheduling is a design constraint, not an afterthought.

CPU utilisation
\[U = \sum \frac{C_i}{T_i}\]
C_i execution time, T_i period; U ≤ 1 is necessary for any scheduler
Rate-monotonic bound
\[U \le n\,(2^{1/n} - 1)\]
sufficient condition for n tasks under rate-monotonic scheduling; tends to ln 2 ≈ 0.693
EDF bound
\[U \le 1\]
sufficient and necessary on a single processor for earliest-deadline-first

09Digital twins and smart infrastructure

A digital twin is a model kept current by sensor data, used for monitoring, simulation and prediction. On infrastructure it appears as structural health monitoring on a bridge, leak detection in a water network, or occupancy control in a building.

The value depends on the loop closing: a model that predicts a bearing failure is useless unless the maintenance system acts on it. A twin also inherits every weakness of its data — drift, missing readings and a changed baseline after renovation.

10Security and privacy by design

Every connected sensor is an attack surface. Common failures are default passwords, unsigned firmware, unencrypted links and no way to patch devices already installed.

Practical defences are device identity and mutual authentication, TLS on the link, signed firmware updates and network segmentation, so a compromised sensor cannot reach the control system.

Privacy is a design constraint too: collect the minimum, aggregate at the edge, and keep personal data out of places it is not needed. A smart water meter that reveals when nobody is home is a privacy problem, not just a utility.

Data minimisation at the edge
send aggregate, not raw: (mean, count, timestamp)
fewer bytes and less personal information leave the device

11Virtual sensing and the hidden state

Not everything worth knowing has a dedicated sensor. Virtual sensing infers a hidden quantity from observable signals through a model: a camera image yields depth, a Wi-Fi signal-strength fingerprint yields indoor position, and a smartphone's inertial readings yield walking speed. The pattern is always observable signals → model → hidden state.

Virtual sensors cut hardware cost and can cover places a physical probe cannot reach, but they inherit model error and drift, so they need periodic re-calibration against ground truth. Treat their output as an estimate with a confidence, and keep the fallback: when the model is uncertain, refuse to act rather than act wrong.

Key terms

Transducer
A device that converts one form of energy, such as strain or temperature, into an electrical signal.
Aliasing
The false low-frequency reading produced when a signal is sampled too slowly for its highest frequency.
Edge inference
Running a trained model on the local device or gateway instead of sending data to the cloud.
MQTT broker
The server that receives published messages and forwards them to subscribers by topic.
Digital twin
A model of a physical asset kept current by sensor data and used for monitoring and prediction.
Age of information
The age of the newest sample that has been processed, used to judge whether a decision is fresh enough.
Rate-monotonic scheduling
A fixed-priority scheme in which shorter-period tasks get higher priority, optimal among static priority assignments.
Virtual sensing
Inferring a hidden quantity such as location or depth from observable signals through a model instead of a dedicated sensor.
Worked example

Can the edge keep up with the stream?

A vibration sensor produces 20 samples per second. The edge model takes 40 ms per sample. The cloud model takes 80 ms of compute plus 50 ms of network time. Find the service capacity of each option, the edge utilisation, and the mean waiting time if the edge queue behaves as an M/M/1 system. Which placement works?

  1. Edge capacity = 1 / 0.040 = 25 samples per second. Cloud capacity = 1 / 0.130 = 7.7 samples per second.
  2. Cloud utilisation with λ = 20 samples per second is 20 × 0.130 = 2.6, which exceeds 1, so the cloud queue grows without bound and no average delay exists.
  3. Edge utilisation is ρ = 20 × 0.040 = 0.8, which is stable but heavily loaded.
  4. For an M/M/1 queue, L_q = ρ²/(1 − ρ) = 0.64/0.20 = 3.2 samples waiting on average.
  5. Mean waiting time = L_q / λ = 3.2 / 20 = 0.16 s, so the mean time in the system is about 0.16 + 0.04 = 0.20 s.
AnswerOnly the edge placement is stable at 20 samples per second. The cloud cannot keep up, and the edge gives a mean decision age around 0.20 s, which is acceptable for vibration monitoring but would need load shedding if the sensing rate rose.

Exam method

  • State the bottleneck stage before proposing an architecture; latency and energy questions are marked on the trade-off, not the product name.
  • In queueing questions, compute ρ = λ t_service first: if ρ ≥ 1 the queue is unstable and no average delay exists.
  • Match range, data rate and power to the application before naming a protocol, and say why the alternatives lose.
  • When a task table appears, compute U = Σ C_i/T_i first, then apply the rate-monotonic or EDF bound, and state the assumption that deadlines equal periods.
