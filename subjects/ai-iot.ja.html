センサー、小型コンピュータ、ネットワーク、モデルが現実の制約のもとで協調して動作する。この科目は最も賢いアルゴリズムよりも、レイテンシ、エネルギー、帯域幅、鮮度、そしてそれらのトレードオフが接続されたインフラにとって何を意味するかに重点を置く。

01デバイスではなくループ

AIoTは推論をデータが生成される場所の近くに置く。システムはトランスデューサでセンシングし、マイクロコントローラで信号を調整し、ネットワーク経由で転送し、判断に基づいて動作する。

通常のIoTと異なるのは、モデルが判断を下す点であり、多くの場合デバイス上で行われる。設計上の問いは決して精度だけではない。エネルギー、レイテンシ、帯域幅あたりの精度である。

ミリ秒単位で報告する橋梁のひずみセンサーは、1時間に一度起動する土壌プローブとは異なる問題を解いている。

ナイキストのサンプリング定理
\[f_s > 2 f_{\max}\]
関心のある最高周波数の2倍を超えてサンプリングする。そうしないと速い振動が偽の遅い波としてエイリアシングされる

02センシング、サンプリング、マイクロコントローラ

センサーは物理量を電気信号に変換し、ADCがそれを固定のサンプリングレートで数値に変換する。実際の測定値にはノイズやドリフトが含まれるため、基準に対して校正し、フィルタリングする必要がある。ただし、すべてのフィルタは遅延を追加することを忘れてはならない。

マイクロコントローラはGPIOピン、タイマー、ローカルチップ用のI²CやSPIなどのバスを提供し、デューティサイクル動作が必要である。無線とセンシングが電力予算の大部分を占めるため、サンプル間でスリープすることがバッテリーを何年も持たせる鍵となる。

ADC分解能
\[\Delta V = \frac{V_{\mathrm{ref}}}{2^n}\]
nビット変換器の最小電圧ステップ。実際の測定値は通常数ステップ分になる

03ネットワークの選択肢

すべての展開に適合する単一の無線は存在しない。リンク層より上では、MQTTが一般的なメッセージングパターンである。デバイスはsite/42/temperatureのようなトピックでブローカーにパブリッシュし、サブスクライバーがそれを受信する。

QoSレベル0、1、2は配信保証と引き換えに重複を許容し、retainedメッセージは遅れて参加したサブスクライバーが古い状態を見るのを防ぐ。

MQTTで測定値をパブリッシュする
client.publish('site/42/strain', payload, qos=1) client.subscribe('site/42/command')
qos=1は少なくとも1回の配信を保証するため、ハンドラは重複を許容する必要がある
典型的なAIoT展開向けの無線オプション
無線典型的な範囲データレート電力典型的な用途
Wi-Fi数十メートル高高カメラ、ゲートウェイ、屋内センサー
BLE約10 m低非常に低ウェアラブル、ビーコン、スマートフォン接続
LoRaWAN2～15 km非常に低非常に低土壌プローブ、地方のメーター
NB-IoT数キロメートル低低公共料金メーター、街路設備

04MQTT以外のプロトコル

MQTTだけがバイトを運ぶ方法ではない。CoAPはHTTPの要求–応答モデルをUDP上に縮小し、制約されたノード向けにconfirmableメッセージとサーバープッシュ用のobserveモードを提供する。これはおしゃべりなWebアプリよりも、ゲートウェイ背後のバッテリーセンサーに適している。

単純なHTTP/RESTはデバッグと統合が容易だが、メッセージあたりの冗長性が高い。WebSocketsはライブダッシュボード用に永続チャネルを維持し、AMQPはゲートウェイ群向けにエンタープライズルーティングを追加する。

習慣ではなく制約で選ぶこと。ペイロードとヘッダのオーバーヘッド、接続状態、配信保証、そしてネットワークがエンドツーエンドでIPか、ゲートウェイ変換が必要かである。常時接続のTCPを前提とするプロトコルは、1時間に一度起動するノードには不適切である。

メッセージングプロトコルの比較
プロトコルトランスポートパターン最適な用途
MQTTTCPトピックによるパブリッシュ–サブスクライブ多数のデバイスから多数のアプリケーションへのテレメトリ
CoAPUDP要求–応答、observe制約されたバッテリーノード、ローカルディスカバリ
HTTP/RESTTCP要求–応答クラウドAPIと単純な統合
WebSocketTCP永続的な双方向ライブダッシュボードと遠隔コマンド

05エッジかクラウドか

推論はデバイス上、ゲートウェイ上、またはクラウドで実行できる。より近くに押し出すとレイテンシと帯域幅は削減されるが、モデルサイズとエネルギーが制限される。エンドツーエンドのレイテンシは各段階の合計であり、最も遅い段階が支配する。

モデル圧縮はエッジ推論を実用的にする。量子化は重みを32ビットではなく8ビットで保存し、プルーニングは小さな重みを除去する。どちらもわずかな精度を犠牲にする。この選択はスローガンではなくトレードオフ曲線として扱うべきである。

エンドツーエンドのレイテンシ
\[L = t_{\mathrm{sense}} + t_{\mathrm{queue}} + t_{\mathrm{compute}} + t_{\mathrm{network}}\]
各段階を測定する。間違った段階を最適化しても何も得られない
サービス容量
\[C = \frac{1}{t_{\mathrm{service}}}\]
サービス時間が秒の場合、1秒あたりのサンプル数

06学習コントローラ：ルールから勾配へ

オンデバイスAIはしばしば視覚モデルではなく学習コントローラである。ルールベース層は固定しきい値で切り替え、学習層は特徴量から線形スコアを計算し、シグモイド関数で確率に変換する。

訓練は交差エントロピー損失の勾配を降下させることで重みを見つける。この損失は自信のある誤りをためらいがちな誤りよりもはるかに大きく罰する。

ワークフローは数学と同じくらい重要である。動作中のコントローラからラベル付き挙動を収集し、実行時に同じ特徴量を抽出し、オフラインで訓練し、その後小さなモデルをオンラインで実行する。モデルは物理ではなく判断パターンを学習するため、部屋を理解せずに教師の挙動を再現する。だからこそ訓練データはエッジケースを網羅しなければならない。

線形スコア
\[s = w_1 x_1 + w_2 x_2 + w_3 x_3 + b\]
特徴量xは最近の測定値から計算される。s = 0が決定境界
シグモイド確率
\[p = \frac{1}{1 + e^{-s}}\]
pは正クラスの予測確率
交差エントロピー損失
\[l = -[y\ln p + (1-y)\ln(1-p)]\]
y ∈ {0, 1}はラベル。自信のある誤答は大きな損失を生む
勾配更新ステップ
\[w \leftarrow w - \eta (p - y) x\]
ηは学習率。訓練サンプルごとに1小ステップ

07ストリーミング、キュー、鮮度

センサーデータは連続的に到着するため、AIoTシステムは待ち行列システムである。到着率がサービス率に近づくにつれて待ち時間は爆発的に増加する。利用率80%では、待ち行列はすでに50%の場合の4倍の長さになる。

アドミッション制御はキューが満杯のときにどのサンプルを破棄するかを決定し、これが過負荷時にシステムが自己保護する方法である。もう一つの有用な指標は情報の経年、つまり最新の処理済みサンプルの年齢である。古いデータに対する非常に正確な推論は、最新の粗い回答よりも悪い。

利用率
\[\rho = \lambda t_{\mathrm{service}}\]
安定した待ち行列にはρが1未満である必要がある
リトルの法則
\[L = \lambda W\]
システム内の平均アイテム数は到着率×システム内の平均時間に等しい
平均待ち時間、M/M/1待ち行列
\[L_q = \frac{\rho^2}{1 - \rho}\]
ρが1に近づくにつれて発散する

08小型コア上のリアルタイムスケジューリング

スケジュール通りにサンプリング、送信、推論を行わなければならないエッジノードはリアルタイムシステムである。各タスクには周期と最悪実行時間、そして決して逃してはならないデッドラインがある。最初のチェックは利用率、つまりすべてのタスクの周期に対する実行時間の合計である。

レートモノトニックは最短周期のタスクに最高優先度を与え、固定優先度スキームの中で最適であることが証明されている。最早デッドラインファーストは残りデッドラインで順序付けし、単一プロセッサを完全利用率まで忙しく保つことができる。

問題では通常、タスク表が与えられ、その集合がスケジュール可能かどうかを尋ねられる。利用率を計算し、限界と比較し、レートモノトニックの場合は各タスクの応答時間も確認する。インフラ監視でデッドラインを逃すことはアラームの喪失を意味するため、スケジューリングは後付けではなく設計制約である。

CPU利用率
\[U = \sum \frac{C_i}{T_i}\]
C_iは実行時間、T_iは周期。U ≤ 1はどのスケジューラにも必要
レートモノトニック限界
\[U \le n\,(2^{1/n} - 1)\]
レートモノトニックスケジューリング下のnタスクに対する十分条件。ln 2 ≈ 0.693に近づく
EDF限界
\[U \le 1\]
単一プロセッサ上の最早デッドラインファーストに対する十分かつ必要条件

09デジタルツインとスマートインフラ

デジタルツインはセンサーデータによって最新に保たれるモデルであり、監視、シミュレーション、予測に使用される。インフラでは、橋梁の構造ヘルスモニタリング、水道網の漏水検知、建物の在室制御として現れる。

その価値はループが閉じるかどうかにかかっている。軸受故障を予測するモデルは、保守システムがそれに基づいて行動しなければ役に立たない。ツインはまた、データのあらゆる弱点を継承する。ドリフト、欠測値、改修後のベースライン変化である。

10設計段階からのセキュリティとプライバシー

接続されたすべてのセンサーは攻撃対象面である。よくある失敗は、デフォルトパスワード、署名されていないファームウェア、暗号化されていないリンク、既に設置されたデバイスをパッチ適用する方法がないことである。

実用的な防御は、デバイスIDと相互認証、リンク上のTLS、署名付きファームウェア更新、ネットワークセグメンテーションであり、これにより侵害されたセンサーが制御システムに到達できなくなる。

プライバシーも設計制約である。最小限を収集し、エッジで集約し、個人データを不要な場所に置かない。誰も家にいないときを明らかにするスマート水道メーターは、単なるユーティリティではなくプライバシー問題である。

エッジでのデータ最小化
send aggregate, not raw: (mean, count, timestamp)
デバイスから出るバイト数と個人情報が少なくなる

11仮想センシングと隠れた状態

知る価値のあるすべての量に専用センサーがあるわけではない。仮想センシングはモデルを通じて観測可能な信号から隠れた量を推論する。カメラ画像から深度を、Wi-Fi信号強度フィンガープリントから屋内位置を、スマートフォンの慣性測定値から歩行速度を得る。パターンは常に観測可能な信号 → モデル → 隠れた状態である。

仮想センサーはハードウェアコストを削減し、物理プローブが届かない場所をカバーできるが、モデル誤差とドリフトを継承するため、定期的にグラウンドトゥルースに対して再校正する必要がある。その出力は信頼度付きの推定値として扱い、フォールバックを維持する。モデルが不確かなときは、誤って行動するよりも行動を拒否する。

Worked example

エッジはストリームに追いつけるか？

振動センサーは1秒あたり20サンプルを生成する。エッジモデルはサンプルあたり40 msかかる。クラウドモデルは計算に80 ms、ネットワーク時間に50 msかかる。各オプションのサービス容量、エッジの利用率、エッジキューがM/M/1システムとして動作する場合の平均待ち時間を求めよ。どの配置が機能するか？

  1. エッジ容量 = 1 / 0.040 = 1秒あたり25サンプル。クラウド容量 = 1 / 0.130 = 1秒あたり7.7サンプル。
  2. λ = 1秒あたり20サンプルでのクラウド利用率は20 × 0.130 = 2.6で、1を超えるため、クラウドキューは無限に成長し、平均遅延は存在しない。
  3. エッジ利用率はρ = 20 × 0.040 = 0.8で、安定しているが負荷が高い。
  4. M/M/1待ち行列では、L_q = ρ²/(1 − ρ) = 0.64/0.20 = 平均3.2サンプルが待機している。
  5. 平均待ち時間 = L_q / λ = 3.2 / 20 = 0.16 sなので、システム内の平均時間は約0.16 + 0.04 = 0.20 sである。
Answer1秒あたり20サンプルで安定するのはエッジ配置のみである。クラウドは追いつけず、エッジは平均判断経年約0.20 sを与える。これは振動監視には許容できるが、センシングレートが上がれば負荷制御が必要になる。

Exam method

  • アーキテクチャを提案する前にボトルネック段階を明示する。レイテンシとエネルギーの問題は製品名ではなくトレードオフで採点される。
  • 待ち行列の問題では、まずρ = λ t_serviceを計算する。ρ ≥ 1なら待ち行列は不安定で平均遅延は存在しない。
  • プロトコルを挙げる前に範囲、データレート、電力をアプリケーションに適合させ、代替案がなぜ劣るかを述べる。
  • タスク表が出たら、まずU = Σ C_i/T_iを計算し、次にレートモノトニックまたはEDF限界を適用し、デッドラインが周期に等しいという仮定を述べる。

Whyビット数が少ないとメモリが減り演算が速くなるが、重みが粗くなるため精度は通常わずかに低下する。

WhyCoAPはWebの要求–応答パターンをUDP上に縮小し、制約されたデバイスが低オーバーヘッドで小さなメッセージを交換できるようにする。
