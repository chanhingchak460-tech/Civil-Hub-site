建物を図面ではなく構造化された情報として記述する：単一の統合モデル、定義された要件、そして各段階を通じたデータ交換の管理された方法。BIMマネジメントは、その情報を信頼できるものにするための規律である。

01モデルは主題の半分にすぎない

ビルディングインフォメーションモデリングは、単一の巧妙なファイルではなく、構造化されたデジタル情報によって建物を記述する。各専門分野は独自の情報コンテナ（モデル、スケジュール、レポート）を作成し、それらのコンテナは所有権を統合せずに調整された状態を保つフェデレーテッドモデルへとまとめられる。

3D画像は目に見える部分だが、価値はそれに付随するデータにある：要素が何であるか、どこに属するか、いくらかかるか、いつ設置されるか、誰が責任を負うか。用途と要件が定義されていないモデルは、高価な図面にすぎない。

02次元：3Dから7Dへ

次元はジオメトリに何が重ねられるかを表す。

  • 3Dは調整された空間モデルである。
  • 4Dは要素を施工活動にリンクすることで時間を加える。
  • 5Dは数量と単価を通じてコストを加える。
  • 6Dはエネルギーと持続可能性の分析を加える。
  • 7Dは運用・保守情報を扱う。

これらの名称は用途の略称であり、成熟度のはしごではない：プロジェクトは5Dコストモデルなしで4Dを使用できる。次元を加えることは規律を加えることを意味する：スケジュールは維持され、コストデータは価格付けされ、資産データは構造化されなければならない。だからこそBIMの用途は想定されるのではなく、合意され範囲が定められる。

Dimension stack
3D geometry → + 4D time → + 5D cost → + 6D energy → + 7D operation
each dimension is a use layered on the same model, not a replacement

03ISO 19650と要件の連鎖

現代のBIMマネジメントは情報要件の連鎖に基づいている。組織情報要件（OIR）が戦略を定め、資産情報要件（AIR）とプロジェクト情報要件（PIR）へと連鎖し、これらが合わさって各契約の交換情報要件（EIR）となる。発注者は要求し、デリバリーチームはそれをどのように満たすかを記述したBIM実行計画（BEP）で応答する。

同じ連鎖が情報モデルを通じて続く：プロジェクト情報モデルはデリバリー中に作成され、資産情報モデルは引き渡し後の運用を支える。この規律とは、正しい情報を、正しい人々に、正しい形式で、正しい時に届けることである。

Requirements chain
OIR → AIR / PIR → EIR → BEP → TIDP + MIDP → information containers
trace any deliverable back to its owner and purpose

04EIRとBEP：情報に関する契約

EIRは、どの情報が、いつ、誰によって、どの詳細度で、どの形式で交換されるかを定義する。価格付けと検査が可能なほど正確でなければならず、曖昧な要件は誰も使えないモデルを生む。情報要求レベルは、各段階で実際にどれだけのジオメトリ、データ、文書が必要かを明確にする。

デリバリーチームは二度応答する。契約前BEPはアプローチ、能力、キャパシティを示し、契約後BEPは方法、標準、CDE、デリバリー計画を定める。タスクチームは自らの成果物についてTIDPを作成し、リードコンサルタントがそれらをMIDPに統合する。

05情報要求レベル

情報要求レベルは曖昧な詳細ラベルに取って代わる：各要素と段階について、各用途がどれだけのジオメトリ、英数字情報、文書を必要とするかを明示する。扉は施工時に完全な3Dジオメトリを必要とするかもしれないが、引き渡し時には防火等級、金物セット、保守間隔だけが必要かもしれない — どこでもより多くの詳細は美徳ではなくコストである。

用途ごとにレベルを設定することで、過少モデリング（モデルのふりをした図面）と過剰モデリング（誰も読まないジオメトリ）の両方を防ぐ。実際には、チームはこれをEIRとBEPに、モデル要素対段階の表として書き込み、各作成者が詳細の期限を正確に把握し、それに対して検査できるようにする。

Level of information need
need = geometry + alphanumeric information + documentation
three columns defined per element and per stage; agree them before modelling starts

06共通データ環境

CDEはプロジェクト情報の単一の情報源であり、共有フォルダではなく管理されたワークフローを持つ。情報は4つの状態を経る：

  • 作業中は作成者に属する。
  • 共有済みは検査済みでチームが利用できる。
  • 公開済みは定義された目的のために承認されている。
  • アーカイブ済みは記録として保持される。

各状態には命名、リビジョン、ステータスコードの規則とアクセス権限がある。CDEはフェデレーションが行われる場所でもある：専門分野モデルは作成者へのリンクを失うことなくレビューのために統合される。

07命名、分類、データ品質

信頼できる交換は命名から始まる。すべての情報コンテナは、コード化されたフィールド（プロジェクト、作成者、ボリューム、レベル、タイプ、リビジョン）から成る一意の識別子を持ち、固定の区切り文字で区切られ、安全な文字セットに制限される。何も符号化しない名前は一人の作成者には問題ないが、40のフェデレーションには管理不能である。分類はオブジェクトを認識された作業分解の体系に整合させ、スケジュールとコスト計画がモデルを自動的に利用できるようにする。

データ品質は層ごとに検査される：

  • ジオメトリが正しく見えるかを確認する目視検査、
  • プロパティが定義され、妥当で、一意であることを確認する整合性検査、
  • 合意された各用途に必要な情報が存在するかのルールベース検査。

検査は紛争の後ではなく、すべての交換の前に予定される。

Container identifier
project-originator-volume-level-type-revision
hyphen-separated alphanumeric fields; every revision of every file stays traceable
Layered model check
quality = visual check + integrity check + rule check
run all three before shared status, on a fixed schedule
Never share what you have not checked A shared container that fails the integrity check becomes the source of everyone else's errors. Run the checks, record the result, then move the status.

08干渉検出と調整

干渉検出は、現場の問題になる前に専門分野モデル間の幾何学的な衝突を見つける。

  • ハード干渉は2つの部材が同じ空間を占めることである。
  • ソフト干渉は設置、アクセス、保守のためのクリアランス不足である。
  • 論理干渉は順序の衝突であり、未完了の活動によって作業が妨げられる場合などである。

ソフトウェアは候補を見つけるだけである。有用なワークフローは、許容差と優先度でヒットを絞り込み、責任ごとにグループ化し、モデルを変更すべきチームに発行し、その後で検査を再実行する。誤検出を想定し、許容差はBEPで合意する。

09能力、成熟度、契約前段階

誰かを任命する前に、クライアントは能力を試す：候補チームはこのプロジェクトが必要とする情報管理プロセスを実行できるか？構造化された能力評価は、標準、セキュリティ、モデリングプロセス、CDE経験を問い、その回答は装飾ではなく入札評価に反映される。成熟度は、組織が孤立した図面作成から完全に管理された情報交換への道のどこに位置するかを表す。

多段階調達ではこれは早期に行われる：能力は入札時に評価され、契約前BEPがアプローチを示し、契約が契約後BEPとデリバリー計画を確定する。評価を省略することは、方向転換がはるかに高くつくプロジェクト中盤に発見コストを先送りするだけである。

Pairwise model interfaces
\[\frac{n(n-1)}{2}\]
with n discipline models, the number of pairwise combinations a federation must keep coordinated

10ライフサイクルを通じたBIM

各段階には適切な用途がある。初期段階では既存条件、敷地分析、設計オーサリングが必要であり、設計調整では空間調整と設計レビューが必要であり、施工では4Dシーケンス、5Dコスト、現場計画、製作が加わり、引き渡しでは竣工情報と運用のための資産モデルが作成される。

資産情報はプロセス全体を試す：保守チームがモデル内で設備、その位置、履歴を見つけられなければ、デリバリーは最後の段階で失敗している。引き渡し時にどの資産データが必要かは、後ではなく最初に決めるべきである。

プロジェクト段階別のBIM用途
段階典型的な用途主な情報成果物
戦略定義要件と能力評価OIR、AIR、最初のEIR
設計設計オーサリング、レビュー、空間調整フェデレーテッド設計モデルと干渉レポート
施工4Dシーケンス、5Dコスト、現場計画調整済みモデル、数量、竣工更新
引き渡しと運用竣工モデリングと資産管理資産情報モデルと資産データ

11モデルを取り巻く技術

モデルは取得と提示の技術に囲まれている。レーザースキャンとフォトグラメトリは既存条件を点群（数百万の測定された3D点）として取得し、そこから竣工モデルがトレースされる。スキャン密度が詳細を決める：点間隔を半分にすると1平方メートルあたりの点数は4倍になる。ドローンは取得を屋根や敷地全体に広げ、IoTセンサーは施工中および運用中に実際の性能をモデルへフィードバックする。

VRは関係者を未建設の設計の中に置いてレビューさせ、ARは測設、検査、保守のためにモデル情報を実際の現場に重ね合わせる。各技術は特定のギャップ（取得、レビュー、フィードバック）を埋めることでその価値を得るが、それぞれがCDEが吸収すべきデータ管理の負担をもたらす。

Point cloud density
\[\rho = \frac{1}{d^2}\]
d is the point spacing in metres and ρ the points per square metre; finer spacing costs scanning time and file size

12役割、責任、限界

情報管理は一つの役職ではなく機能の集合である。発注者は情報マネージャーを持ち、デリバリーチームは独自のものを持ち、各タスクチームはマネージャー、情報マネージャー、調整のためのインターフェースマネージャーを持ち、情報作成者は自らのコンテンツを作成し所有する。責任マトリクスは各コンテナを作成、検査、レビュー、承認する者を記録する。

BIMには述べておくべき限界がある。ソフトウェア間の相互運用性は依然として不完全であり、オープン形式と合意された標準が重要である；データ品質は規律ある検査に依存する；訓練、ライセンス、調整時間にはコストがかかる。便益はソフトウェアではなくマネジメントから生まれる。

Key terms

フェデレーテッドモデル
別々の専門分野モデルから組み立てられ、各作成者の所有権を手放さずにリンクされたレビュー用モデル。
情報コンテナ
モデル、図面、スケジュール、レポートなど、名前を付けられバージョン管理された情報のパッケージ。
交換情報要件
どの情報を、いつ、どの形式で納品しなければならないかについての発注者の表明。
BIM実行計画
要求された情報をどのように作成・管理するかを記述したデリバリーチームの応答。
共通データ環境
管理された状態、命名、アクセス規則を備えた、合意されたプロジェクト情報の単一の情報源。
干渉検出
統合モデルにおける物理的な重なり、クリアランス不足、順序の衝突を自動的に検査すること。
情報要求レベル
各要素、段階、用途がどれだけのジオメトリ、情報、文書を必要とするかの表明。
点群
レーザースキャンやフォトグラメトリによる測定された3D点の大規模な集合で、既存条件の取得に用いられる。
Worked example

施工段階の干渉チェックのための情報フロー

クライアントの交換情報要件は、毎月のマイルストーンで調整済みフェデレーテッドモデルを要求し、干渉は合意された許容差で解決されることとしている。この要件がクライアントから解決済み干渉までどのように伝わるか、またマイルストーンが達成された証拠として何が数えられるかを説明せよ。

  1. クライアントの組織要件とプロジェクト要件がEIRに反映される：調整済みモデル、毎月、指定された許容差と形式で。
  2. デリバリーチームはBEPで応答する：フェデレーション戦略、モデル標準、CDEワークフロー、責任マトリクス、マイルストーン日程。
  3. 各タスクチームのTIDPが自らのモデルと納品日を明示し、モデルは作成され、自己検査され、CDEの作業中にアップロードされる。
  4. 情報マネージャーがステータスとリビジョンコードを検査し、承認されたモデルを共有済みに移し、調整のためにフェデレーションする。
  5. 干渉ルールが実行される：ハード干渉はゼロ許容差、クリアランス干渉はプロジェクト許容差。ヒットは絞り込まれ、グループ化され、責任あるタスクチームに発行される。
  6. タスクチームはモデルを修正し、ルールが再実行され、その後でのみ調整済みモデルがマイルストーン向けに公開され、資産データは引き渡しモデル向けに予定される。
Answer再実行で合意された干渉が閉じられ、調整済みモデルが公開ステータスでCDEに承認されたときに要件は満たされる。証拠は、ソフトウェアが衝突が残っていないと主張することではなく、干渉レポートを伴う公開済みモデルである。

Exam method

  • 要件の連鎖をフローとして学ぶ；ほとんどの問題はどのソフトウェアを使うかではなく、どの文書を誰が所有するかを問う。
  • CDEの状態を順に述べ、各状態で何が変わりうるかを言う — 共有済みは検査済みであり最終ではない。
  • ハード、ソフト、論理干渉をそれぞれ具体的な例を一つ挙げて区別する。
  • 便益を問われたら、単なる協働の改善ではなく、プロジェクト段階と情報成果物を挙げる。
  • クライアントがBIMのリスクをどう低減するかを問われたら、連鎖を挙げる：入札時の能力評価、契約前BEP、契約上の契約後BEP、そして各交換前の予定された検査。

Q01クライアントがデリバリーチームにどの情報をいつ交換するよう要求するかを述べる文書はどれか？

WhyEIRは発注者の要件であり、BEPとTIDPはそれに対するデリバリーチームの応答である。

Q02共通データ環境において、検査済みでデリバリーチーム全体が利用できるが、まだクライアント向けに承認されていない情報はどの状態か？

Why共有済み情報はチームの検査を通過している；公開済み情報は定義された目的のために承認されている。

Q03ソフト干渉は最も適切には次のどれと説明されるか：

Whyソフト干渉はクリアランスまたはアクセスの問題であり、ジオメトリの重なりはハード干渉、順序の問題は論理干渉である。

Q044D BIMはモデルを何にリンクするか？

Why4Dはモデル要素を活動と日付にリンクすることで時間を加える；コストは5D、運用は7Dである。

Why要素と段階ごとに必要なジオメトリ、英数字情報、文書の組み合わせを定義し、作成者が過少にも過剰にもモデリングしないようにする。

Q06能力評価は主に何のために用いられるか：

Whyクライアントは任命前に候補チームのプロセス、標準、CDE経験を評価し、入札判断が主張ではなく証拠に基づくようにする。
