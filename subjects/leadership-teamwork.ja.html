人々が実際にどのように協働するか：コミュニケーションのループ、共感とIステートメント、すべてのチームが通過する段階、そして対立を有益に保つフィードバック。エンジニアリングプロジェクトは計算ではなくチームによって遂行される。

01コミュニケーションこそが仕事

プロジェクトでは、失敗のほとんどは計算ミスではない。情報の失敗である：誰も開かなかった図面改訂、会議で提起されたが記録されなかったリスク、作業順序を誤解した作業員。

コミュニケーションは性格の特性ではなく技術的スキルである。送信者がメッセージを符号化し、チャネルを選び、受信者が復号し、フィードバックがループを閉じる。ノイズ——専門用語、騒がしい現場、急いだメッセージ——はあらゆる段階で入り込む。

フィードバックのない一方向の放送はコミュニケーションではなく、単なるアナウンスである。

コミュニケーションループ
Sender → Message → Channel → Receiver → Feedback
フィードバックが証明するまで、ノイズはあらゆる段階で作用する

02共感とIステートメント

共感とは、相手の立場に応答する前に理解しようと試みることである。通常、次のように分けられる：

  • 情動的共感（感情への反応を感じる）
  • 認知的共感（相手が何を考えているかを推し量る）
  • 慈悲的共感（助けたいと動かされる）

エンジニアリングチームでは認知的共感がほとんどの役割を果たす：誤解がどこで起こるかを予測する。

何か問題が起きたとき、「あなたはいつも図面を遅れて送る」のようなyouステートメントをしたくなる。それは非難を割り当て、防御を招く。Iステートメントは行動、感情、具体的な影響を述べ、相手に行動の余地を残す。

Iステートメント
When [behaviour], I feel [feeling] because [impact].
人格ではなく行動を描写する

03チームは段階を通過する

チームが効果的になることはめったに宣言によって起こらない。彼らは認識可能な段階を通過し、リーダーの役割は各段階で変わる。

最初は人々は礼儀正しい。その後、意見の不一致が続くが、それは正常である：役割、基準、権限を交渉する必要がある。そうして初めて共有された習慣が定着する。

実践的な教訓は、落ち込みを予期することである。3週目に議論するチームは、同調したままでアイデアを試さないチームよりも健全なことが多い。

チームの段階とリーダーシップの焦点
段階見え方リーダーシップの焦点
形成期礼儀正しく、役割が不明確目的と基本ルールを設定する
混乱期役割をめぐる摩擦対立を表面化させ、意思決定ルールを設定する
規範期信頼と共有された習慣責任を委譲する
遂行期自己管理された遂行集中を守り、障害を取り除く
解散期総括振り返りと承認

04役割と社会的手抜き

グループは自動的にチームになるわけではない。チームは各人が明確で異なる貢献を持ち、誰が何をしているかを全員が把握できるときに機能する。

責任が曖昧になると、社会的手抜きが現れる：個人の仕事と成果の結びつきが見えないため、努力を減らす。

  • すべてのタスクに名前のある担当者と可視化されたステータスを与える。
  • 貢献をレビュー可能にする。
  • 挑戦者の役割を交代制にし、意見の不一致がリスクではなく義務になるようにする。

これらはいずれも心理的安全性——問題を提起しても罰せられないという共有された信念——なしには存続しない。

05対立とフィードバック

仕事に関する対立はしばしば生産的である；人に関する対立は腐食的である。目的は不一致を取り除くことではなく、証拠と結果に基づかせることである。

建設的フィードバックは、何が起こったか、どのような影響があったか、次にどう変えるかをレッテルなしで述べる。SBIパターンはそれを観察可能に保つ：状況、行動、影響。

「昨日のブリーフィングで杭の位置が言及されなかったため、作業員は間違ったエリアに到着した」は人が変えられることである。「あなたは不注意だ」は変えられない。タイミングは言葉遣いと同じくらい重要である：出来事に近い時期に、非公開で与えられたフィードバックは聞き入れられる；年次レビューのために取っておかれたフィードバックは判決である。

SBIフィードバック
Situation + Behaviour + Impact + next step
観察可能な事実のみ、レッテルなし

06肩書きのないリーダーシップ

状況的リーダーシップは、指示と支援の量を人とタスクに合わせる：新しいタスクには明確な指示が必要で、慣れたタスクには委任が必要である。

変革型リーダーシップは目的と模範を通じて機能する；取引型リーダーシップは明確な交換を通じて機能する。ほとんどのリーダーは両方を混ぜる。

エンジニアはしばしば権限なしでリードする——コンサルタントを調整し、下請け業者を追いかけ、クライアントを説得する。そのとき影響力は信頼性、準備、そして相手の言葉で決定を説明する能力に依存する。だからこそリーダーシップとコミュニケーションは切り離しがたい。

07タスク役割と関係役割

チームには2種類の貢献が必要である：

  • タスク役割は仕事を進める：構造化するオーガナイザー、それを試すチャレンジャー、それを仕上げるフィニッシャー。
  • 関係役割は人々を働かせ続ける：励ます人、調和させる人、静かな同僚に気づいて招き入れるメンバー。

一人が両方を担うことはできるが、どちらか一方だけではチームは存続しない。タスク役割ばかりで関係役割がないと、ストレス下で分裂する有能なチームが生まれる；逆は決して終わらない友好的なチームを生む。

どの役割が欠けているかに注意し、意図的に採用せよ。

役割のバランス
Task roles (organiser · challenger · finisher) + Relationship roles (encourager · harmoniser · gatekeeper)
健全なチームは両方を担う

08決定する会議

決定のない会議は議論であり、チームはそれをあまりにも多く持っている。

  • 事前にアジェンダを送る；目的、項目、各項目の担当者を明記する。
  • 議長、タイムキーパー、議事録係を任命する。
  • 最初の項目の前に意思決定ルール——コンセンサス、多数決、議長が決定——を合意する。
  • すべての項目を決定で締め、すべての決定を担当者と期日で締める。

議事録は意見の記録ではなく、これら2つの事実を記録する。担当者のない決定は提案であり、期日のない決定は願望である。

決定記録
Decision = Option chosen + Owner + Deadline
議事録に記載し、1日以内に回覧する

09動機付けと委任

仕事が意味を持ち、進捗が見え、貢献が認められるとき、人は関与し続ける。動機付けは演説よりも、努力を消耗させる障壁——不明確な範囲、不足するツール、見えない評価——を取り除くことである。

委任は、決定する権限と回復する支援とともにタスクを引き渡すことである。方法ではなく成果を述べよ；チェックポイントを合意せよ；そして次の委任をより大きくできるよう振り返りを行え。

すべての決定を保持したまま仕事を委任することは委任ではなく、待ち行列である。

委任パッケージ
Outcome + Authority + Support + Checkpoint
方法ではなく成果を述べる

10集団意思決定と集団思考

グループはメンバーが単独でするよりも悪い決定をすることがある。集団思考とは、疑念を沈黙させる合意への衝動である：チームはコンセンサスを報い、批判を抑圧し、外部の警告を軽視する。それは過信、外部者のステレオタイプ化、悪い知らせの自己任命検閲者として現れる。

構造で対抗せよ：

  • 討論の前に悪魔の代弁者を任命する
  • 議論の前に書面による意見の沈黙ラウンドを行う
  • 外部者を招いて計画を試す

目標は終わりのない異議ではなく、真の挑戦を生き延びた決定である。

集団思考の危険信号 疑わしいほど迅速に訪れた全会一致、自己検閲（「みんな同意しているから提起しない」）、そして吟味せずに外部の批判を退けること。

Worked example

チームメイトとの難しい会話を始める

チームメイトが共有分析のために約束した2つの締め切りを逃した。次のタスクは1週間後に期限があり、チームの他のメンバーが待っている。誠実で具体的で、チームが機能し続ける可能性が高い会話の冒頭を起草せよ。

  1. 日付と成果物を伴う観察可能な事実を書き出し、動機の解釈は含めない。
  2. 影響を具体的に述べる：下流のタスクが遅れ、待っている間に2人が再配置された。
  3. Iステートメントを使って自分の懸念を表明し、何かを提案する前に開かれた質問をする。
  4. 具体的な変更を1つ、チェックポイント、そして遅れた場合にどうするかを合意し、記録する。
AnswerIステートメントの冒頭：「2つの分析セクションが合意した日付を過ぎて届いたとき、比較を始められず、待っている間に2人が再配置されました。何が妨げになったのか理解したいです。残りのセクションを木曜日までに、正午のチェックポイントと遅れた場合のプランBを付けて合意できますか？」

Exam method

  • 意図ではなく行動と影響を述べよ；意図は見えず、それについて議論することは会話を無駄にする。
  • 修正を処方する前にチームがどの段階にあるかを名指せ——混乱期のチームにはさらなる励ましではなく意思決定ルールが必要である。
  • ケース問題では、コミュニケーションの失敗を診断する際に個人、チーム、システムを分離せよ。
  • フィードバックは非公開で出来事に近い時期に与えよ；公の場での訂正は通常、学習ではなく防御を生む。
  • 失敗しているチームに関するケースでは、タスクのギャップと関係のギャップの両方を名指せ——ほとんどの回答はタスクで止まる。
